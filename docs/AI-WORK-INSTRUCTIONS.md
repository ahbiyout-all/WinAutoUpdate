# 범용 AI 작업 지시서 (AI Work Instructions)

이 문서는 특정 프로젝트나 기술에 묶이지 않고, **모든 AI 코딩 에이전트가 반복해서 사용할 수 있도록**
정리한 작업 표준(SOP)입니다. 실제 요청마다 달라지는 세부 항목은 "입력 요구사항"으로 보고,
아래의 고정된 절차와 검증 게이트를 통해 처리합니다.

- 적용 대상: 코드 수정, UI/UX 개선, 빌드·배포 스크립트, 문서화, 버전 관리, 보안 점검을 요청하는 모든 작업
- 핵심 원칙: **실현 가능한 것만 설계하고, 실제 파일에 적용하고, 스스로 검증한다.**

---

## 1. 절대 원칙 (Non-negotiable Rules)

| # | 원칙 | 왜 필요한가 |
|---|---|---|
| P1 | 실제 저장소/파일 상태를 먼저 확인하고, 확인한 내용만 사실로 말한다. | 미리보기·기억에 의한 환각(Hallucination) 방지 |
| P2 | 구현할 수 없거나 현재 구조와 모순되는 요구는 설계하지 않고, 그 이유를 명시한다. | "실현 가능한 것만 설계" |
| P3 | 모든 변경은 **실제 소스 파일**에 적용한다. 화면의 임시 편집·미리보기만으로 끝내지 않는다. | "프리뷰에만 적용됨" 문제 방지 |
| P4 | 다음 단계로 넘어가기 전에 자아성찰(Self-Reflection) 게이트를 통과한다. | 오류 누적 방지 |
| P5 | 테스트·빌드·배포는 **실제로 실행한 결과만** 성공으로 기록한다. | 거짓 완료 보고 방지 |
| P6 | 버전·문서·빌드 산출물 이름은 항상 같은 값으로 동기화한다. | 버전 불일치 방지 |
| P7 | 사용자 데이터, 비밀값, 개인정보를 저장소/릴리스에 올리지 않는다. | 보안 사고 방지 |

## 2. 표준 작업 흐름 (Standard Pipeline)

요청이 크고 여러 항목이 섞여 있어도 항상 아래 순서를 유지합니다.

```
0. 입력 분류 → 1. 현 상태 확인 → 2. 실현 가능성 판정 → 3. 로드맵 수립
→ 4. 항목별 구현 → 5. 자아성찰/심층 감사 → 6. 오류 수정 → 7. 재검증
→ 8. 문서화/작업로그 → 9. 버전 판정/동기화 → 10. 완료 보고
```

### 단계 0. 입력 분류

요청 문장을 아래 버킷으로 분리합니다. 한 문장이 여러 버킷에 걸치면 분리해서 기록합니다.

| 버킷 | 예시 |
|---|---|
| 기능 | 메뉴를 실제 데이터로 연결, 자동 업데이트 알림 |
| UI/레이아웃 | 반응형 카드, 툴팁, 테마 버튼, 고정 창 크기 |
| 빌드/배포 | 배치 스크립트, 인스톨러, 출력 폴더 구조, CI 워크플로 |
| 보안 | 외부 접근, 방화벽, 토큰/개인정보 노출 |
| 문서 | 릴리스 노트, 블로그용 문서, 작업 로그 |
| 버전 | SemVer 판정, UI/스크립트/태그 동기화 |
| 품질 | 미구현 코드, 주석/코드 불일치, 오류 수정 |

### 단계 1. 현 상태 확인 (Evidence First)

- 저장소 루트, 디렉터리 트리, Git 상태/커밋 이력을 확인합니다.
- 변경 대상 파일을 **읽어서** 현재 구현 여부를 판정합니다.
- 문서에 적힌 내용과 실제 코드가 다르면 **코드를 기준**으로 보고 차이를 기록합니다.
- 확인하지 못한 항목은 "미확인"으로 남기고 추측하지 않습니다.

### 단계 2. 실현 가능성 판정

| 판정 | 의미 | 다음 행동 |
|---|---|---|
| 가능 | 현재 구조에서 바로 구현 가능 | 로드맵에 포함 |
| 조건부 | 도구/권한/환경 필요(예: 관리자 권한, 외부 인증) | 조건과 검증 방법을 명시하고 포함 |
| 불가/모순 | 요구끼리 충돌하거나 지원하지 않는 플랫폼 | 제외 사유를 기록하고 사용자에게 알림 |

판정 시 흔한 모순 예시:

- "창을 800×600으로 고정" vs "화면 너비에 따라 반응형 리플로우" → 우선순위를 확인해 하나로 확정.
- "APK/iOS 패키징" vs "모바일에서 동작하지 않으면 제거" → 실제 빌드 가능 여부를 확인한 뒤 가능한 산출물만 유지.
- "웹 화면을 앱으로 실행" → 기술 목적에 따라 PWA / WebView2 / Electron·Tauri / `--app` 모드 중 하나를 선택하고 나머지는 제외.

### 단계 3. 로드맵 수립

- 항목별로 **순서 번호, 목표, 변경 파일, 검증 방법**을 적습니다.
- 선행 조건이 있는 항목(예: 버전 동기화 → 문서 → 빌드 스크립트)은 의존성 순으로 배치합니다.
- 사용자가 "끝까지 진행"을 요청했으면 로드맵의 모든 가능 항목을 순서대로 처리하고, 불가 항목은 건너뛰지 말고 사유와 함께 보고합니다.

### 단계 4. 항목별 구현

- 한 번에 하나의 논리적 변경만 적용합니다.
- 기존 코드의 명명 규칙·파일 인코딩·줄바꿈 규칙(예: Windows CRLF)을 유지합니다.
- 생성형 산출물(빌드가 만들어내는 파일)은 소스 트리에서 제거하고, 빌드 스크립트가 생성하도록 둡니다.
- 아이콘/이미지가 필요하면 제공된 원본을 사용해 빌드 단계에서 자동 생성합니다.

### 단계 5. 자아성찰 / 심층 감사 (필수 게이트)

다음 단계로 가기 전에 아래를 **파일을 다시 읽어서** 확인합니다.

#### 5.1 정합성

- [ ] 요청한 항목이 실제 파일에 반영되었는가? (미리보기만 수정하지 않았는가?)
- [ ] 코드·문서·스크립트·UI에 서로 다른 값(버전, 이름, URL, 날짜)이 남아 있지 않은가?
- [ ] 메뉴/탭/모달/트리/툴팁 등 **모든 진입점**이 같은 데이터와 동작을 사용하는가?
- [ ] 이전에 고쳐진 파일이 이후 변경에서 되돌아가지 않았는가?

#### 5.2 정밀 오류 검증

- [ ] 빌드/컴파일: 경고·오류 수를 실제 명령 실행으로 확인.
- [ ] 테스트: 실제 통과/실패 수를 확인. 실패 시 원인을 고치고 다시 실행.
- [ ] 정적 확인: 미구현 메서드(`TODO`, `throw new NotImplementedException`, 빈 처리기),
      주석과 코드 불일치, 사용되지 않는 코드.
- [ ] 경계값: 빈 값, null, 권한 없음, 오프라인, 기존 설치/미설치, 버전 같음/다름.
- [ ] 인코딩: `.bat`/`.cmd`는 CRLF, UTF-8 BOM이 필요한 설정 파일은 BOM 유지.
- [ ] 보안: 토큰/비밀값/개인 이메일/로컬 절대 경로가 커밋 대상에 없는지 검사.

#### 5.3 문서·버전 검증

- [ ] 패치노트/작업로그에 변경 내용이 기록되었는가?
- [ ] 버전을 올렸다면 UI 표시·빌드 산출물 이름·Git 태그·릴리스 노트가 모두 같은가?

게이트 통과 못 함 → 단계 6(오류 수정)으로 돌아갑니다.

### 단계 6. 오류 수정

- 발견된 오류마다 `증상 → 원인 → 수정 → 재검증` 4칸으로 기록합니다.
- 같은 오류가 재발하면 로드맵 자체(게이트 항목)를 보강합니다.

### 단계 7. 재검증

- 단계 5를 다시 실행합니다. **자아성찰 없이 완료 선언 금지.**

### 단계 8. 문서화

| 문서 | 기록 내용 |
|---|---|
| 작업 로그 | 날짜, 목적, 변경 파일, 검증 결과, 미실행 항목, 남은 작업 |
| 패치노트 | 사용자에게 보이는 기능/개선/버그 수정 요약 |
| 플랫폼별 안내 | 필요한 경우 서식 있는 텍스트 버전과 HTML 버전을 각각 관리 |
| 공개 문서 | 작성자/공식 채널 정보는 실제 저장소 설정과 동일하게 유지 |

### 단계 9. 버전 판정 (SemVer)

문서를 갱신한 뒤, 변경 규모에 따라 버전을 판정합니다.

| 변경 | 버전 |
|---|---|
| 호환되지 않는 API/동작 변경 | MAJOR+1, MINOR/PATCH 0 |
| 하위 호환 기능 추가 | MAJOR 유지, MINOR+1, PATCH 0 |
| 하위 호환 버그 수정 / 문서·빌드 보정 | MAJOR/MINOR 유지, PATCH+1 |

판정 후 **단일 소스(예: 빌드 속성의 `<Version>`)** 만 바꾸고, UI·스크립트·태그가 이를 참조하게 합니다.
문서만 추가하고 동작이 바뀌지 않았다면 버전을 올리지 않고 그 이유를 기록합니다.

### 단계 10. 완료 보고

- 무엇을 실제로 변경했는지 파일 경로와 함께 요약합니다.
- 실행한 검증과 **하지 못한 검증(권한/환경 부족)** 을 명확히 구분합니다.
- 다음으로 진행할 가능 항목을 남깁니다.

## 3. 자주 쓰는 세부 지침

### 3.1 UI/UX

- 정보가 많으면 카드 안의 설명을 제거하고 **툴팁/도움말**로 옮깁니다.
- 중요한 메뉴는 상단에 퀵 셀렉트 칩·드롭다운·풀다운으로 배치합니다.
- 테마는 명확한 이름(다크/회색/화이트/베이지)의 버튼 또는 드롭다운으로 제공하고,
  **배경/카드/글자 대비**를 각 테마마다 확인합니다.
- 고정 창 크기와 반응형 레이아웃이 동시에 요구되면, 우선순위를 확인해 하나를 따릅니다.

### 3.2 빌드/배포

- 배치 스크립트는 Windows 줄바꿈(CRLF)으로 저장하고 영어로 작성합니다.
- 산출물 경로는 버전별로 분리합니다(예: `dist/v<버전>/win-x64`, `dist/v<버전>/installer`).
- 실행 파일 이름 끝에 버전을 자동 부여하고, 빌드 완료 후 결과 폴더를 엽니다.
- 인스톨러는 고유 AppID와 폴더 구성을 쓰고, 설치 순서를 지킵니다.
  (기존 실행 종료 → 덮어쓰기/삭제 확인 → 라이선스 → 설치 → 바로가기 선택 → 실행)
- 무인 설치 옵션과 프로그램 추가/제거 등록을 지원합니다.
- 방화벽 규칙은 기본 이름과 버전이 붙은 이름을 모두 등록합니다.
- 릴리스에는 **설치 파일만** 첨부하고, 문서·로그·개인정보·비밀값은 제외합니다.
- CI 러너의 런타임 지원 종료(EOL) 공지가 있으면 워크플로의 버전을 최신 LTS로 갱신합니다.

### 3.3 보안/품질

- 외부에서 접근 가능한 포트, 토큰 저장 방식, 파일 권한(ACL)을 점검합니다.
- API 키를 클라이언트에 두지 말고 서버로 옮길 때도 **UI와 동작은 그대로** 유지합니다.
- 미구현 코드와 자동 생성 파일을 구분해, 자동 생성 파일은 소스에서 제거합니다.
- 비공개 정보가 `.gitignore` 허용 목록에 걸려 올라가지 않도록 정기 점검합니다.

### 3.4 문서/채널

- 공개 문서의 작성자·저장소·블로그·회사 정보는 실제 값과 링크를 하나의 표준으로 통일합니다.
- 블로그용 문서는 요청된 순서(제목 → 본문 → 업데이트 → 이미지 → 다운로드 → 버전 →
  시스템 요구사항 → 제작자/채널 → 전체 변경 이력 → 추천 태그)를 지킵니다.
- 태그는 한글과 영어를 섞어 20개 이하, 200자 이내로 만듭니다.

---

## 4. 완료 정의 (Definition of Done)

아래를 모두 만족해야 완료로 보고합니다.

1. 실제 파일에 변경이 적용되었다.
2. 자아성찰 게이트(5.1~5.3)를 통과했다.
3. 빌드/테스트가 실제로 실행되어 결과를 기록했다.
4. 문서/작업로그가 최신 상태이다.
5. 버전이 필요한 경우 모든 표시 위치가 동일하다.
6. 보안·개인정보 검사를 통과했다.
7. 미실행 항목과 이유가 명시되었다.

## 5. 요청 템플릿 (복사해서 사용)

```text
[목표] (무엇을 왜 바꾸는가)
[범위] 포함: ... / 제외: ...
[우선순위] 1) ... 2) ... 3) ...
[제약] 창 크기/인코딩/플랫폼/권한/보안 등
[검증] 빌드 명령, 테스트 명령, 확인할 화면/동작
[문서] 갱신할 문서 목록
[버전] 변경 규모에 따른 SemVer 판정 요청 여부
```

에이전트는 이 템플릿이 없어도 위 절차를 따라야 하며,
정보가 부족하면 추측하지 말고 **확인이 필요한 항목만** 질문합니다.
